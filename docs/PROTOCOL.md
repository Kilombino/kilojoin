# Kilojoin v1 — protocol

Kilojoin is coinjoin for the BLAKE2b chain (BIP-110 + BLAKE2b proof of work). Nobody coordinates it and nobody holds funds: pools are announced on a Nostr relay, and the people in a pool talk through NIP-44 encrypted Nostr events. Each wallet builds the same transaction, checks its own output and change, and signs only its own input. The design follows Joinstr, adapted to how Kilowallet starts a round: people join an open pool, and once enough are in, anyone can ask to close it and the rest vote.

This document describes v1 exactly as implemented in:

- Kilowallet (Android): `app/src/main/java/com/kilombino/pyblockwatch/coinjoin/`
  - `Protocol.kt`: constants, messages, hashes
  - `PoolSession.kt`: the state machine
  - `CoinjoinTx.kt`: the transaction
  - `Nip44.kt`, `NostrEvent.kt`, `RelayClient.kt`
- Kilojoin (server and StartOS): <https://github.com/Kilombino/kilojoin>, which compiles those same files.

[`vectors.json`](vectors.json) holds test vectors generated by that code from fixed keys. The tool that prints them is `src/main/kotlin/com/kilombino/kilojoin/tools/Vectors.kt`.

Both implementations interoperate today: rounds have run phone↔StartOS, and on mainnet.

## 1. Transport

| | |
|---|---|
| Relay | `wss://relay.kilombino.com` (strfry). Any NIP-01 relay works if every participant uses the same one. |
| Pool announcement | kind **32022**, parameterized replaceable: `d` = pool id, `t` = `kilojoin`, `network` = `blake2b`. Plaintext JSON, signed by the **pool key**. |
| Pool messages | kind **2023**, tag `p` = recipient, content NIP-44 v2. |
| Keys | Every pool has its own fresh secp256k1 key (the pool key). Every join uses its own fresh join key. No long-term identity is involved. |

### 1.1 Pool announcement (kind 32022)

```json
{"v":1,"app":"kilowallet","network":"blake2b","id":"<16 hex>","public_key":"<pool pub, x-only hex>",
 "denomination":10000,"fee_rate":2.0,"min_peers":2,"max_peers":5,"private":false,
 "timeout":1791400000,"state":"open","peers":1}
```

- `state` is one of `open`, `closing`, `done` or `aborted`.
- `peers` is the number of seats taken.
- `timeout` is the unix time at which an open pool expires.

The creator republishes the announcement on every change.

A client accepts an announcement only if all of these hold:

- `pubkey == public_key` and `d == id`;
- `v == 1` and `network` matches;
- `1 000 ≤ denomination ≤ 100 000 000` (Kilowallet itself lists and creates only from 10 000);
- `2 ≤ max_peers ≤ 20` and `2 ≤ min_peers ≤ max_peers`;
- `1 ≤ fee_rate ≤ 500` sat/vB.

Lists show only pools with `state == open`, `timeout > now` and `peers < max_peers`.

### 1.2 Messages (kind 2023)

| Flow | Author → `p` | NIP-44 conversation key |
|---|---|---|
| join request | join key → pool pub | ECDH(join secret, pool pub) |
| welcome / reject | pool key → join pub | ECDH(pool secret, join pub) |
| **pool channel** (everything else) | pool key → pool pub | ECDH(pool secret, pool pub) |

Once welcomed, a member holds the pool secret. From then on every channel message is authored by the pool key and encrypted to itself, so on the relay all members look like one author.

## 2. Messages

All payloads are JSON with a `type`. Hex is lowercase.

### Seat

A seat is a member's coin and change, as everybody sees it:

```json
{"token_hash":"<sha256 hex>","coin":{"txid":"<64 hex>","vout":0,"value":50000,"pubkey":"<33-byte compressed hex>"},
 "change_script":"<hex or empty>","change_value":39729}
```

- The input is always **P2WPKH**: its script is derived from `coin.pubkey`.
- `change_value` is 0 (and `change_script` empty) when there is no change.

### Join → pool (direct)

```json
{"type":"join","seat":{…,"token_hash":""},"proof":"<DER>","change_sig":"<DER>","pw":"<hex, private pools only>"}
```

- **Ownership proof:** ECDSA (RFC 6979) by the coin's key over
  `sha256("kilojoin/v1/own|<pool id>|<join pub>|<txid>:<vout>|<value>")`.
  For the creator's own seat, the pool pub stands in for the join pub.
- **Change signature:** ECDSA by the coin's key over
  `sha256("kilojoin/v1/change|<pool id>|<txid>:<vout>|<change script hex or empty>|<change value>")`.
  This binds the change to the coin, so nobody else can swap it.
- **Password (private pools):**
  - `pw_key = sha256("kilojoin/v1/pw|<pool id>|<password>")`
  - `pw = HMAC-SHA256(pw_key, <join pub as ASCII hex>)`
  - The password itself never travels, and a captured proof is useless for any other join key.

### Pool → joiner (direct)

```json
{"type":"welcome","pool_secret":"<hex>","token":"<32 hex>","seq":3}
{"type":"reject","reason":"…"}
```

- The joiner checks that `pubOf(pool_secret) == pool pub`. Anyone can write to a join key, but only the real pool knows that secret.
- `token` is the member's seat secret. Only `sha256("kilojoin/v1/token|" + token)` (the `token_hash`) appears in rosters.
- `seq` is the number of the roster that holds the new seat.

### Pool channel

| type | from | payload | effect |
|---|---|---|---|
| `roster` | creator | `seq`, `seats[]` | Members apply only a `seq` higher than the last one they saw (replays on reconnect are ignored). A member missing from it is out. |
| `close_request` | any member | `token`, `vote_id` (16 hex) | Opens a vote if `seats ≥ min_peers`. The requester counts as yes. The creator sends one by itself when the pool is full. |
| `vote` | member | `token`, `vote_id`, `accept` | Read by the creator. A "no" leaves the round (that member's coin is free) and the pool reopens. |
| `reopen` | creator | `vote_id` | Back to open. |
| `closing` | creator | `seats[]` (the round), `deadline` | Round fixed; members not in it are out. |
| `output` | member | `script` (must match `^0014[0-9a-f]{40}$`, P2WPKH) | The member's mixed output, posted **without any identity** after a random delay of 3–43 s. |
| `sig` | member | `outpoint`, `sig` (DER + sighash byte) | Verified by everyone against the plan. |
| `tx` | member | `txid` | Someone broadcast it; the others check the txid matches the plan. |
| `leave` | member | `token` | The member gives up the seat. If the creator leaves, the pool is aborted. |
| `abort` | anyone | `reason` | Round over; nothing was signed by those who abort before `sig`. |

The `token` in `close_request`, `vote` and `leave` is how a member proves which seat it holds. Only `token_hash` is public.

## 3. Round

```
creator: announce (state open) + roster(seq 1, own seat)
joiners: join ─► creator checks ─► welcome + roster(seq n) + announce(peers n)
any member (seats ≥ min_peers): close_request ─► VOTING (10 min)
   all yes ─► closing      a "no" ─► reopen (the "no" leaves)
   deadline: yes ≥ min_peers ─► closing with the yes-voters only
             else ─► silent members are dropped from the roster, reopen
CLOSING (5 min + 60 s grace): every member posts its output after a random delay
   outputs == round size ─► SIGNING;  more outputs than people ─► abort
SIGNING (20 min + 60 s grace): each member checks the plan, signs its input, posts `sig`
   all sigs ─► anyone assembles and broadcasts, posts `tx`
BROADCAST ─► CONFIRMED at 1 confirmation
pool timeout while open ─► aborted ("the pool expired")
```

What the creator checks on a join:

- the pool is open and not full, and the password is right;
- the seat parses, and the coin has no seat yet;
- the ownership proof is valid;
- `change_value` equals the expected change (§4);
- the change signature is valid;
- the coin is unspent on the chain with exactly that value (`gettxout`, mempool included).

That gives one seat per coin, with a real coin behind it.

Every message is replayed from the relay on reconnect, so every step must be idempotent.

## 4. Transaction

### Fees

Every participant pays the same fixed share, known at join time:

```
fee_share(rate, change) = ceil(rate × (68 + 31 + (31 if change) + 10.5/2))   // vbytes: P2WPKH in, mix out, change out, half the overhead
change = coin − denomination − fee_share(rate, true), if that is > 294 (dust);
         otherwise 0, and the coin must still cover denomination + fee_share(rate, false)
minimum coin ("exact coin") = denomination + fee_share(rate, false)
```

At 2 sat/vB this gives 271 sats with change and 209 without, so the exact coin for a 10 000 pool is 10 209.

### Building the transaction

- Version 2, locktime 0, every sequence `0xfffffffd`.
- **Inputs:** sorted by `(txid, vout)`, where txid is in display byte order and compared as a hex string.
- **Outputs:** first the mix outputs (`denomination` each), sorted by script hex; then the change outputs, sorted by script hex.

`plan()` refuses the transaction if:

- there are fewer than 2 inputs;
- the number of mix outputs differs from the number of inputs;
- a coin appears twice;
- any output script appears twice, or pays back to an input's script;
- a change output is dust;
- the fee is negative.

### Checks before signing

- Our mix script appears exactly once with exactly `denomination`.
- At least `n` outputs carry `denomination`.
- Our change is present with exactly our value.
- `fee ≥ floor(rate × vsize × 0.95)` and `fee ≤ n × fee_share(rate, true) + n × 295`.

### Signature

- ECDSA (RFC 6979, low-R ground), sighash byte **0x21** = `SIGHASH_UNIFIED | SIGHASH_ALL`. This is the BLAKE2b fork's opt-in replay protection (`doc/unified-sighash.md` in Bitcoin Knots v29.4.1+ on the BLAKE2b branch).
- A node without the fork cannot reconstruct the message, so the coinjoin is valid only on the BLAKE2b chain.
- The txid does not cover witnesses, so every member knows it before anyone signs.

`vectors.json` → `transaction` contains, for a 2-person round:

- the input and output order;
- both unified sighashes;
- both signatures;
- the final raw transaction and its txid.

A BIP-110 node decodes it.

## 5. Pool options

| | Range | Notes |
|---|---|---|
| Denomination | 10 000 – 100 000 000 sats (1 000 on test networks) | Chosen by whoever opens the pool. |
| Fee rate | 1 – 500 sat/vB | Fixed for the pool; each person pays `fee_share`. |
| People | min 2–20, max 2–20 | The round may close with any count from `min_peers` up. |
| Open for | creator's choice (Kilowallet: hours) | `timeout` in the announcement. |
| Private | password | HMAC proof (§2). The password is shared outside the protocol. |
| Exact coin | wallet feature | A payment to yourself of `denomination + fee_share(rate, false)`, paid with **unmixed** coins only. It then joins with no change. |
| Relay | one per deployment | All participants must use the same relay. |

## 6. Relay (relay.kilombino.com)

| | |
|---|---|
| Software | strfry. NIP-11: max message 524 288 bytes, max subscriptions 200, max limit 500. |
| Authentication | none needed to read or write (NIP-42 is advertised but not required). |
| Write policy | spam filters plus a per-pubkey daily event limit. Because a pool channel is one pubkey, kinds 2023/32022 must be exempt for pools beyond a handful of people (being checked). |
| Retention | no expiry is set on Kilojoin events and the relay does not prune them on a schedule; a pool's history is what a reconnecting member replays. |
| Tor | no onion address yet. Clients can reach it through Tor as a clearnet relay. |
| Client behaviour (ours) | ping after 60 s of silence; reconnect after 120 s; on reconnect, re-subscribe to `#p:[join pub]` and `#p:[pool pub]` with no `since`, and replay. |

## 7. Hardware signing

Not possible today without work on both sides:

- **Sighash:** inputs are P2WPKH signed with sighash 0x21, the BLAKE2b unified sighash. Krux, SeedSigner and other hardware signers do not implement it.
- **Joining:** the ownership proof and the change signature are ECDSA signatures over custom 32-byte hashes, not a transaction.
- **No PSBT:** the protocol moves raw signatures, not PSBTs. A PSBT export/import of the final plan would be easy to add (the plan is fully determined before signing).
- **Time:** the signing window is 20 minutes, enough for an animated-QR round trip. The output window (5 min) needs no signer.

---

## 8. Ark

There is no Ark-specific code in Kilojoin yet.

- **Mix, then move into Ark (board):** works today by hand. Board from the mixed output alone, without combining it with other coins, or the mix is undone.
- **An Ark funding output directly in the coinjoin:** would need the board's exit data saved before anyone can broadcast, as noted. It would also need the output to be a P2TR script, which v1's `^0014…` rule forbids. That is a v2 change.

## 9. Privacy: what is and is not protected

- **Inputs and changes are public to the pool:** every member sees every seat (coin + change), and the chain shows them afterwards anyway. The change output is linked to its input, as in any coinjoin with change. Exact coins avoid change.
- **Mixed outputs carry no identity:** they are posted on the shared pool channel (the pool key), after a random delay. No member, not even the creator, learns from the protocol which mixed output belongs to which input.
- **The relay operator can link them:** the relay sees which WebSocket connection (and so which IP address) published each `output` event, and which connection joined. Running over Tor, ideally a different circuit for outputs, avoids this. The same holds for anyone who can watch a participant's network.
- **Timing:** the 3–43 s random delay is weak against a determined observer of the relay.
- **The creator** learns which coins joined, which they would anyway, and holds the roster. It cannot steal: every member verifies the transaction before signing.
- **Members can disrupt a round:** every member holds the pool secret, so any member can post channel messages as "the pool". A malicious member can:
  - post extra outputs, which aborts the round;
  - withhold its signature, which aborts at the deadline;
  - forge roster or closing messages, which can exclude people.

  None of this can move funds. There is no blame or ban mechanism in v1.
- **Change addresses** come from the participant's own wallet, so they are only as private as that wallet's address handling.

Present it as experimental: correct for funds, modest for privacy against the relay.
